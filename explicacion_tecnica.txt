1. JUSTIFICACIÓN DE LA ESTRUCTURA DE CARPETAS
──────────────────────────────────────────────

La estructura sigue Clean Architecture (Robert C. Martin) adaptada a Python/
FastAPI. Se divide en 5 capas con responsabilidades claramente delimitadas:

  /app
    /api              → Capa de presentación (Interface Adapters)
    /core             → Infraestructura transversal (Cross-cutting Concerns)
    /domain           → Capa de dominio (Entities)
    /use_cases        → Capa de aplicación (Application Business Rules)
    /infrastructure   → Capa de infraestructura (Frameworks & Drivers)

¿Por qué esta separación y no un simple "models/views/services"?

a) Regla de Dependencia (Dependency Rule):
   Las dependencias apuntan SIEMPRE hacia adentro. `domain` no importa nada
   de `infrastructure`. `use_cases` depende de `domain` pero NUNCA de `api`.
   Esto permite reemplazar PostgreSQL por DynamoDB, o OpenAI por Ollama, sin
   tocar una sola línea de lógica de negocio.

b) Principio de Inversión de Dependencias (DIP — SOLID):
   En `domain` se definen interfaces abstractas (ports). En `infrastructure`
   se implementan (adapters). Los `use_cases` operan contra abstracciones,
   no contra implementaciones concretas. Esto hace el sistema testeable con
   mocks sin levantar servicios externos.

c) Single Responsibility Principle (SRP):
   - `api/` solo se preocupa de recibir HTTP requests y devolver responses.
   - `use_cases/` orquesta flujos (extraer CV → enriquecer → persistir).
   - `infrastructure/` maneja la comunicación con el mundo exterior.
   - `core/` centraliza configuración, excepciones y dependency injection.

d) Escalabilidad horizontal:
   Cuando el sistema crezca, cada capa puede subdividirse en módulos de
   feature (ej. /domain/cv/, /domain/candidate/) sin romper la arquitectura.
   Un Modular Monolith que puede evolucionar a microservicios si es necesario.


2. BENEFICIOS DE POETRY SOBRE requirements.txt
───────────────────────────────────────────────

a) Resolución determinista de dependencias:
   Poetry genera un poetry.lock que congela TODAS las dependencias
   transitivas. requirements.txt con pip freeze es un snapshot plano sin
   grafo de resolución — si dos paquetes necesitan versiones incompatibles
   de una misma dependencia, pip lo instala silenciosamente y explota en
   runtime. Poetry lo detecta ANTES de instalar.

b) Separación dev / producción:
   Poetry permite [tool.poetry.group.dev.dependencies] para herramientas
   como pytest, ruff, mypy. En producción se instalan solo las deps de
   runtime con `poetry install --only main`. Con requirements.txt esto
   requiere mantener dos archivos (requirements.txt + requirements-dev.txt)
   que inevitablemente se desincronizan.

c) pyproject.toml como Single Source of Truth:
   Toda la configuración del proyecto (metadatos, dependencias, linting,
   testing, type checking) vive en un solo archivo estandarizado por
   PEP 621. No hay setup.py, setup.cfg, MANIFEST.in, tox.ini dispersos.

d) Gestión de entornos virtuales:
   Poetry crea y gestiona el virtualenv automáticamente. Elimina el
   clásico problema de "¿activé el venv correcto?" y el drift entre
   lo que está instalado y lo que dice el archivo de dependencias.

e) Versionado semántico con caret (^):
   Las versiones como "^0.115.0" permiten actualizaciones de patch y minor
   automáticas pero bloquean breaking changes. Es un balance entre
   estabilidad y mantenerse actualizado sin intervención manual.


3. CONFIGURACIÓN DE main.py — PREPARACIÓN PARA ESCALABILIDAD
─────────────────────────────────────────────────────────────

a) Application Factory Pattern (create_app):
   No se crea la instancia de FastAPI a nivel de módulo de forma monolítica.
   Se usa una función factory que:
   - Permite crear instancias AISLADAS para tests (cada test suite puede
     tener su propia app con configuración diferente).
   - Facilita la inyección de configuraciones alternativas (staging, prod).
   - Hace explícito el orden de inicialización: settings → middleware →
     routers.

b) Lifespan Context Manager (asynccontextmanager):
   Reemplaza los decoradores @app.on_event("startup") y
   @app.on_event("shutdown") que están DEPRECATED desde FastAPI 0.109+.
   El lifespan es el patrón recomendado oficialmente y permite:
   - Inicializar connection pools a la DB al arrancar.
   - Cerrar conexiones limpiamente al apagar.
   - Gestionar el ciclo de vida de clientes HTTP (httpx.AsyncClient).

c) Configuración centralizada con pydantic-settings:
   - Validación de tipos en tiempo de arranque (fail-fast). Si falta
     OPENAI_API_KEY, la app NO arranca. No hay errores silenciosos.
   - @lru_cache en get_settings() crea un singleton que se lee una sola
     vez del .env y se reutiliza en toda la aplicación.
   - En tests: get_settings.cache_clear() permite inyectar configuraciones
     distintas sin monkey-patching.

d) CORS configurable por entorno:
   Los orígenes permitidos se leen de variables de entorno, no están
   hardcodeados. En desarrollo se permite localhost:3000; en producción
   se restringe al dominio real. allow_methods está explícitamente listado
   (no se usa el wildcard ["*"]) para cumplir con el principio de mínimo
   privilegio.

e) Documentación condicional:
   /docs y /redoc se deshabilitan en producción (docs_url=None). Exponer
   la documentación interactiva de la API en producción es un vector de
   ataque para reconocimiento. En desarrollo y staging siguen disponibles.

f) Healthcheck separado en su propio router:
   El endpoint GET /health vive en app/api/health.py, no inline en main.py.
   Esto sigue SRP y permite escalar el healthcheck para incluir:
   - Verificación de conectividad a la DB.
   - Estado del cliente OpenAI.
   - Latencia de servicios dependientes.
   Sin contaminar el punto de entrada de la aplicación.


4. DECISIONES ADICIONALES Y ADVERTENCIAS
─────────────────────────────────────────

a) Se incluyeron dependencias no solicitadas explícitamente pero necesarias:
   - python-multipart: Requerido por FastAPI para file uploads (CVs en PDF).
     Sin esta dependencia, los endpoints de upload fallan con ImportError.
   - httpx: Cliente HTTP async para comunicación con Supabase REST API y
     para tests con TestClient de FastAPI (que lo requiere internamente).

b) Se incluyó toolchain de desarrollo en pyproject.toml:
   - ruff: Reemplaza flake8 + isort + black en una sola herramienta.
     Escrito en Rust, es ~100x más rápido que sus equivalentes en Python.
   - mypy (strict): Type checking estático. Con strict=true se fuerza
     tipado explícito en toda la codebase.
   - pytest + pytest-asyncio: Framework de testing con soporte async nativo.

c) Se agregó .gitignore para proteger el archivo .env con secrets reales.

1. RESILIENCIA CON TENACITY
───────────────────────────

Las llamadas a LLMs externos son inherentemente frágiles. Para garantizar
la robustez de la API en producción, se incorporó la librería `tenacity`
al `AIExtractor`.

El método `extract()` fue decorado con:
    @retry(
        wait=wait_exponential(multiplier=1, min=2, max=10),
        stop=stop_after_attempt(3),
        retry=retry_if_exception_type((LLMRateLimitError, LLMTimeoutError)),
        reraise=True,
    )

¿Por qué estos parámetros exactos?
- wait_exponential(min=2, max=10): Backoff exponencial truncado. Empieza
  esperando 2s, luego 4s, 8s, hasta un máximo de 10s. Este patrón es
  crítico para recuperarse de Rate Limits (HTTP 429) sin abrumar al
  provider con retries inmediatos que solo exacerbarían el bloqueo.
- stop_after_attempt(3): Límite máximo de 3 intentos totales (la llamada
  original + 2 retries). Si el servicio sigue caído, preferimos fallar
  rápido y liberar los threads de FastAPI en lugar de quedarnos colgados.
- retry_if_exception_type: SOLO reintenta en errores transitorios (Timeouts
  y Rate Limits). Si el error es de autenticación o de validación de modelo,
  NO se reintenta, ya que fallaría de nuevo de todas formas.


2. GROQ COMO PROVEEDOR LLM PARA EL MVP
──────────────────────────────────────

Groq utiliza LPUs (Language Processing Units) que ofrecen latencias muy
inferiores a los GPUs tradicionales, ideal para tareas en tiempo real.

Para utilizar Groq sin reescribir código, aprovechamos que su API es 100%
compatible con la especificación de OpenAI.

Configuración aplicada (vía variables de entorno):
- OPENAI_BASE_URL=https://api.groq.com/openai/v1
- OPENAI_MODEL=llama3-8b-8192

Ventajas de esta arquitectura:
- Portabilidad Total: El código de `AIExtractor` usa el SDK oficial de
  OpenAI y es completamente agnóstico al modelo o proveedor subyacente.
  Moverse de Groq de vuelta a OpenAI o a un LLM open source local (Ollama)
  es una operación de Zero-Code-Change (solo requiere cambiar el .env).
- Optimización de Costos: Groq suele ser más económico y rápido para
  modelos open-source que los modelos propietarios.
- Control de Rate Limits: Los límites de cuota (Rate Limits) suelen ser
  más estrictos en tiers gratuitos de proveedores como Groq. Aquí es donde
  el uso de `tenacity` (documentado arriba) brilla como mecanismo de
  protección fundamental.

## Registro 9: Persistencia Asíncrona y Aislamiento de Dominio (Fase 4)
- ¿Por qué SQLAlchemy 2.0 sobre SQLModel? Aunque SQLModel reduce código, acopla la capa de dominio (esquemas) con la de infraestructura (tablas). En Clean Architecture, el dominio no debe saber cómo se guarda en disco. Al usar SQLAlchemy 2.0 puro, protegemos los modelos de Pydantic y garantizamos un rendimiento asíncrono óptimo con `asyncpg`.
- El Patrón Repositorio facilita inyectar dependencias y realizar mocks durante las pruebas unitarias sin levantar contenedores de PostgreSQL.
## Registro 13: Empaquetado y Reproducibilidad (Fase 6)
- ¿Por qué Docker? Un evaluador técnico no debería perder tiempo configurando entornos virtuales, instalando dependencias o levantando motores de bases de datos locales. Docker Compose garantiza que la arquitectura (API + PostgreSQL) se ejecute con un solo comando, demostrando empatía por la Developer Experience (DX) y estándares reales de la industria.

  Registro 10: Implementación de SQLAlchemy 2.0 y Repositorio
  Fecha: 2026-07-23
  Fase: 4 — Persistencia y Flujo HITL
================================================================================

1. SQLALCHEMY 2.0 CON TIPADO ESTRICTO (Mapped[T])
─────────────────────────────────────────────────

Se implementó SQLAlchemy 2.0 aprovechando al máximo sus nuevas
capacidades de tipado estático con `DeclarativeBase` y `Mapped[T]`.

Por qué esta sintaxis moderna:
- Permite a `mypy` validar los tipos de las columnas en tiempo
  de desarrollo, reduciendo errores en producción.
- Evita los "magic methods" antiguos de SQLAlchemy 1.4.
- El tipo `JSONB` de PostgreSQL se mapea de forma natural a
  diccionarios de Python, permitiendo guardar el resultado estructurado
  de la IA (`extracted_data`) con índices GIN en el futuro.

2. EL PATRÓN REPOSITORIO (PORT & ADAPTER)
─────────────────────────────────────────

El Patrón Repositorio es la piedra angular para aislar la Base de Datos
del resto de la aplicación.

- Puerto (Dominio): `DocumentRepository` es una clase abstracta pura
  (ABC). Solo conoce tipos genéricos (UUIDs, diccionarios, strings) y el
  esquema de negocio (`ExtractionResult`). No sabe nada de PostgreSQL.
- Adaptador (Infraestructura): `PostgresDocumentRepository` hereda
  del ABC e implementa los métodos inyectando un `AsyncSession`.

Beneficios clave para la API (Fase 5):
a) Endpoints Limpios: Los routers de FastAPI solo inyectarán la interfaz
   abstracta. No habrá queries SQL (`select(DocumentModel)`) mezcladas en
   los endpoints. Esto cumple el principio de Responsabilidad Única.
b) Testabilidad: Durante los tests unitarios, los casos de uso (Fase 5)
   pueden recibir un `MockRepository` en memoria sin necesidad de
   levantar Testcontainers o bases de datos temporales.
c) Flexibilidad: Si el volumen de documentos escala y decidimos mover
   los resultados a MongoDB (Document Store), solo necesitamos crear un
   `MongoDocumentRepository` sin alterar ni una sola línea de lógica
   de negocio ni de los endpoints.

1. LA IMPORTANCIA DE AISLAR LA RED Y LA BASE DE DATOS
─────────────────────────────────────────────────────

En la arquitectura empresarial moderna, las pruebas unitarias deben ser:
- Rápidas (cientos de tests ejecutados en milisegundos).
- Deterministas (no deben fallar si el WiFi o el proveedor externo fallan).

Por ello, en esta suite (`tests/use_cases/test_extraction.py`), prohibimos
estrictamente cualquier llamada HTTP real hacia Groq/OpenAI, así como consultas
reales a PostgreSQL.

Para lograrlo, utilizamos `unittest.mock.AsyncMock`. Inyectamos una clase 
"fantasma" (mock) como dependencia del Caso de Uso, que simula devolver 
instancias Pydantic válidas o levantar `LLMExtractionError` simulando un fallo
de red en `tenacity`.

2. VALIDACIÓN DE REGLAS DE NEGOCIO EN PYDANTIC
──────────────────────────────────────────────

Las pruebas de dominio (`tests/domain/test_schemas.py`) verifican
que nuestra lógica de negocio principal no dependa de controladores (API).

Se demostró que la entidad `ExtractionResult` es dueña de su propio flujo:
- Si el LLM reporta un `confidence_score` menor a 0.85, la entidad
  automáticamente enciende la bandera `requires_human_review = True`,
  lo que garantiza que la API ponga el documento en estado `PENDING`.
- A su vez, `StatusUpdateRequest` previene que un mal actor (o un bug del frontend)
  envíe estados no permitidos como "IN_PROGRESS", levantando un `ValidationError`
  gracias a las restricciones nativas de Pydantic.

Con esta suite, el Core de la aplicación está blindado contra regresiones.

1. OPTIMIZACIÓN Y AISLAMIENTO (DOCKERIGNORE)
────────────────────────────────────────────

Al empaquetar una aplicación para producción, el "build context" de Docker
envía por defecto todo el directorio raíz al daemon de Docker.
La creación del archivo `.dockerignore` es crucial por dos razones:

- Seguridad (Prevenir fugas): Excluimos el archivo `.env` y el directorio `.git`.
  Si un `.env` local con una API Key real se copia accidentalmente dentro de la
  imagen de Docker, cualquiera que tenga acceso a la imagen podría extraer la llave.
  En nuestra arquitectura, las variables se inyectan en tiempo de ejecución (runtime)
  a través de `docker-compose.yml`.
- Rendimiento (Imágenes Ligeras): Al bloquear entornos virtuales (`.venv`), cachés
  pesados (`__pycache__`, `.pytest_cache`), y PDFs de prueba, reducimos drásticamente
  el tamaño de la imagen final y aceleramos el tiempo de construcción (build time).

2. CONTROL DE VERSIONES (GITIGNORE)
───────────────────────────────────

El archivo `.gitignore` estandariza el repositorio para cualquier desarrollador
que lo clone en el futuro:
- Previene que secretos (`.env`) suban a GitHub.
- Mantiene el repositorio limpio de archivos autogenerados por Python (`*.pyc`)
  o por el IDE (`.vscode/`).
- Hemos excluido explícitamente `*.pdf` y la carpeta `Pruebas/` para garantizar
  que los datos de prueba y currículums sintéticos no se persistan en el control
  de versiones, cumpliendo con buenas prácticas de sanitización de datos.

Con esto, el proyecto garantiza un "Developer Experience" (DX) impecable: el
evaluador técnico clonará el código, agregará su `.env` y ejecutará Docker Compose
sin fricción, encontrando una arquitectura limpia y auditable.

1. ALINEACIÓN DE NEGOCIO (EL README.md)
───────────────────────────────────────

El README del proyecto no es un simple manual técnico. Fue estructurado para 
responder directamente a los criterios de evaluación de Dev Talenty, fungiendo 
como un Documento de Diseño (RFC/Design Doc) ejecutivo:

- Matriz de Priorización: Se justificó la elección de la Extracción de CVs como 
  el MVP, balanceando el impacto inmediato en el reclutamiento vs el costo 
  técnico. Se descartaron opciones puramente deterministas (Validación ERP) 
  para demostrar el uso correcto del filtro IA vs Reglas.
- Diseño de Solución: Se explicó la justificación del Enfoque Híbrido. Usar 
  solo LLMs para extraer PII es peligroso; usar solo Regex es frágil. PyMuPDF + 
  Presidio + Instructor(LLM) proveen el pipeline ideal.
- Costos y Riesgos: Se documentó la mitigación de la latencia usando Groq (LPUs) 
  y Llama-3.3-70b (Open Source) para evitar el vendor lock-in costoso de OpenAI, 
  así como la mitigación de seguridad bloqueando el envío de PII a APIs públicas.

2. AUDITORÍA DEVSECOPS Y SANITIZACIÓN FINAL
───────────────────────────────────────────

Antes del release final, el repositorio fue auditado para cumplir con 
políticas estrictas de Zero-Secret-Leakage:

a) Generación de .env.example:
   Se extrajeron las llaves del `.env` local, construyendo una plantilla limpia 
   `.env.example` que preserva la estructura de configuración (incluyendo los 
   strings de conexión PostgreSQL locales y flags como DEBUG=true) pero enmascara 
   la `GROQ_API_KEY`. Esto permite una clonación Zero-Friction por parte del 
   evaluador.

b) Purga de Contexto Interno:
   Se eliminaron completamente del sistema de archivos y del trackeo de Git 
   los archivos `contexto_asistente.md` y `contexto_antigravity.md`, los cuales 
   contenían instrucciones de orquestación interna irrelevantes para la evaluación 
   final. El proyecto expone exclusivamente el código fuente, el README.md y esta 
   explicación técnica.

c) Validación de Índice de Git:
   Se verificó vía `git status` que el archivo `.gitignore` configurado 
   previamente estuviera operando correctamente. Entornos virtuales, 
   archivos .env locales, PDFs de prueba y directorios de caché han quedado 
   completamente aislados del commit final de entrega.
